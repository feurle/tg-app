# Single container: Spring Boot serves the built frontend directly

As a solo developer we were running the React frontend and the Spring Boot backend as two separate Docker images (`feurle/tg-app`, `feurle/tg-web`), each with its own GitHub Actions pipeline, its own nginx (in `tg-web`, proxying `/api` to the backend), and its own Docker tags. This doubled the build effort per change, and desynced versioning: `next-version.sh` ran independently in both pipelines, `release.yml` triggered off either one finishing, and only the backend image ever got the immutable SemVer tag — the frontend image never did, even though both were considered part of the same release.

We decided to build the frontend (`frontend/dist/`) as part of the Gradle build and copy it into `src/main/resources/static`, so Spring Boot serves it directly. This collapses to one Docker image, one GitHub Actions pipeline (`deploy.yml`, extended with a `frontend/**` path trigger), one version, and one release. `tg-web`'s Dockerfile, its nginx config, the `frontend-deploy.yml` workflow, and the `tg-web-*` compose services are removed. The external `nginx-proxy` + `acme-companion` (TLS termination and host routing across the whole Hetzner box, unrelated to this app's internal structure) is unaffected, except that `VIRTUAL_HOST`/`LETSENCRYPT_HOST` now point at `tg-app` instead of `tg-web`. The security headers previously set in `tg-web`'s nginx config move into Spring Security's header configuration.

## Consequences

- Frontend and backend are now always versioned and deployed together; there is no way to ship a frontend-only hotfix without a full Gradle/Java build.
- `frontend/dist/` must never be committed to git or hand-edited in `src/main/resources/static`; it's fully regenerated by the build (a `Sync`-style Gradle task should clear stale assets before copying).
- Local development is unaffected: the frontend still runs standalone via `npm run dev` on 5173 proxying to the backend on 8080, per the "Frontend" section of the root `AGENTS.md`.
